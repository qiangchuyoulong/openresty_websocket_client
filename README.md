# WebSocket 网关模块功能说明文档

## 模块概述

这是一个基于 OpenResty Lua 生态开发的 WebSocket 反向代理网关模块，核心作用是在 Nginx Worker 进程内部维护与多个后端 WebSocket 服务的长连接池，对外提供高可靠的请求转发能力。模块通过协程隔离、信号量同步、心跳保活等机制，解决了传统短代理模式下的连接复用率低、后端服务压力大、请求状态难追踪等问题，适用于聊天、游戏等需要长连接交互的实时业务场景。


## 核心依赖

模块基于以下成熟开源组件构建，保证了运行稳定性：

- `resty.websocket.client`：OpenResty 官方提供的高性能 WebSocket 客户端库，用于建立与上游服务的长连接
- `cjson.safe`：安全模式的 JSON 编解码库，避免非法输入导致协程崩溃
- `ngx.semaphore`：基于 Nginx 共享内存的轻量级信号量，用于协程间的高效同步

## 核心架构设计

模块采用 **单 Worker 多长连接 + 双协程驱动** 的架构模式，每个上游服务在当前 Nginx Worker 中仅维护一条 WebSocket 长连接，所有业务请求全部复用该连接，从根本上减少了与后端服务的握手开销。

### 核心数据结构

模块内部通过全局表维护所有运行状态，各表职责明确无交叉：

| 数据结构 | 作用说明 |
| --- | --- |
| `UPSTREAMS` | 上游服务配置表，预定义不同业务类型后端的连接地址、端口和路径 |
| `conns` | 存储当前 Worker 中与各个上游建立的 WebSocket 客户端连接对象 |
| `send_q` | 每个上游对应一个独立的发送队列，所有待发送的消息先入队再串行消费 |
| `send_sema` | 每个上游对应一个信号量，用于唤醒发送协程，实现消息的异步非阻塞投递 |
| `pending` | 全局请求等待表，以自动生成的 reqid 为键，存储所有正在等待上游响应的请求上下文 |
| `req_seq` | 全局自增请求序列号，用于生成全局唯一的请求 ID |

## 核心运行协程

每个上游服务都会独立启动两个常驻后台协程，分别负责收包和发包逻辑，完全隔离读写操作，避免协程竞争：

### reader_loop 读循环

这是上游连接的收包与健康检测核心协程，主要职责包括：

1. 持续从 WebSocket 连接中读取上游返回的帧，单次 recv 超时设为 5 秒，实现轮询式唤醒
2. 对不同类型的帧做分类处理：收到 ping 自动回复 pong，收到 pong 刷新活性时间，收到业务帧将数据写入对应请求的响应缓存
3. 内置三级健康检测机制：任何帧都会刷新最后活跃时间，超过 90 秒未收到任何帧直接判定连接死亡，触发重连逻辑
4. 连接异常断开时自动进入指数退避重连流程，重连间隔从 1 秒逐步递增到最大 60 秒，避免后端服务恢复时被大量重连请求打垮
5. 连接断开或重连时，主动唤醒所有等待该上游响应的挂起请求，返回明确的错误信息，避免协程永久死锁

### sender_loop 写循环

这是唯一持有上游 WebSocket 连接写权限的协程，核心作用是串行消费发送队列，彻底避免多协程并发写同一个 WebSocket 连接导致的帧混乱问题：

1. 等待信号量唤醒，批量消费发送队列中的所有待发送消息
2. 自动区分消息类型：处理 ping 心跳帧、close 关闭帧和普通业务文本帧，调用对应的 WebSocket 发送接口
3. 连接不可用时自动丢弃队列中的消息，避免无效发送引发的错误日志泛滥
4. Worker 进程退出时自动清空队列、关闭连接，优雅释放底层 socket 资源

### 全局 Watchdog 监控协程

作为全局守护协程，每 0.5 秒检测一次 Worker 进程的退出状态，一旦收到 Nginx 的优雅退出信号，立刻执行全量资源清理：

1. 强制关闭所有上游 WebSocket 长连接，避免产生 CLOSE-WAIT 残留套接字
2. 主动唤醒所有发送协程，跳过信号量等待直接退出
3. 遍历所有 pending 表中的挂起请求，全部标记为完成并返回关闭提示，防止 Nginx 退出时出现协程泄漏

## 对外接口说明

模块对外仅暴露两个核心接口，使用方式极其简洁，业务侧无需感知底层长连接的维护细节：

### `_M.init()`

Worker 进程初始化阶段调用的启动函数，执行逻辑包括：

1. 为每个上游服务初始化发送队列和信号量对象
2. 尝试预连接所有配置的上游服务，预连接失败不阻塞启动，后续由 reader_loop 自动重试
3. 启动所有上游的读循环、写循环协程，同时启动全局 Watchdog 守护协程

### `_M.call(name, msg)`

业务请求上下文调用的核心转发接口，执行流程如下：

1. 首先检查对应上游的连接是否可用，连接已断开直接返回上游不可用错误
2. 生成全局唯一的 reqid，将当前请求的上下文（响应缓存、完成标记、独立信号量）存入 pending 表
3. 将封装好的请求体写入对应上游的发送队列，通过信号量通知发送协程投递消息
4. 进入等待循环，最多等待 60 秒，上游每返回一帧业务数据就唤醒一次协程，直到收到标记 `done=true` 的结束帧后返回完整的响应数组
5. 支持上游返回多段流式响应，所有片段会按到达顺序完整存入 resp 数组返回给调用方

## 关键特性与优势

1. **零并发写安全**：所有上游的写操作全部在独立的 sender_loop 协程中串行执行，从根源上杜绝了多协程并发写 WebSocket 导致的帧分片错误
2. **精准心跳保活**：每 20 秒主动向上游发送 ping 帧，90 秒无任何数据返回即判定连接死亡，比默认 TCP 超时机制更快发现死连接
3. **请求全链路追踪**：自动生成包含节点 ID、Worker PID、毫秒时间戳、自增序号的全局唯一 reqid，全链路日志可追溯
4. **优雅退出机制**：完全适配 Nginx 的优雅退出流程，所有后台协程都能感知 Worker 退出状态，不会出现阻塞休眠、协程泄漏、套接字残留等问题
5. **低侵入性接入**：业务侧仅需配置上游地址，调用 call 接口即可完成请求转发，无需手动管理 WebSocket 连接状态
